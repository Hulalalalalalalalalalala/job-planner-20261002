# Job Planner

Run a small deterministic file-task plan and persist each result. Python 3.10+ and the standard library are sufficient.

`python3 job_planner.py samples/plan.json` runs three included jobs: line count, SHA-256 and CSV dimensions. It prints completed/failed counts and writes `.results/latest.json`. The plan refers to `samples/notes.txt` and `samples/sales.csv` inside the chosen root. Use `--root` to set that directory and `--output` for a relative report path. `samples/plan-dependencies.json` shows forward references, a failed branch with blocked downstream jobs, and an independent job still succeeding.

Supported operations are count-lines, sha256 and csv-summary. Jobs without dependencies run sequentially in plan order; results have no timestamps so identical inputs produce identical report content. Duplicate job names are rejected. Per-job file or operation errors are recorded and subsequent jobs continue. Exit codes are 0 when all jobs complete, 1 when any job fails or is blocked, and 2 for an invalid plan or report path.

A job may declare `"depends_on": [other job names]`; a missing key or empty list means no dependencies. Names match exactly and may point forward in the plan. The whole dependency graph is validated before anything runs: `depends_on` must be a list of nonblank names with no duplicates, and every name must exist, not be the job itself and not form a cycle. Any violation makes `run_plan` raise `ValueError`; the CLI prints its `{"error": ...}` JSON, returns 2 and leaves any existing report untouched.

On each pass the plan runs the earliest-in-plan pending job whose direct dependencies already have records; dependency-free jobs take part in the same choice. A job executes its operation only when every direct dependency `completed`. If any direct dependency is `failed` or `blocked`, the job does not read its input and is recorded with only `name`, `status: "blocked"` and `blocked_by` (every failing or blocked direct dependency, in `depends_on` order); blocked state propagates downstream and each task produces exactly one record. Results in the report are ordered by actual processing order. When at least one job has a nonempty `depends_on`, the CLI summary adds a `blocked` count (the `failed` count still covers operation failures only); plans without dependencies keep the original summary fields.

To run only part of a plan, pass `run_plan(root, jobs, output, targets=[...])` or repeat the CLI's `--only NAME` once per job. Each target is one exact job name (no case folding or trimming); the run covers the targets plus all their direct and indirect prerequisites — shared prerequisites run once and target order never changes execution order. The whole plan is still validated (names, dependencies, input path boundaries) before the scope is chosen, so errors in unselected branches reject the run. Jobs outside the scope are not read, produce no records and cannot affect the exit code; the report and the returned list contain only the jobs processed this run, and the CLI counts and the optional `blocked` field describe that same scope. An empty or non-list `targets`, non-string or blank entries, duplicates and unknown names all raise `ValueError` (CLI: `{"error": ...}` JSON, exit 2, no tasks run, existing report untouched). Omitting `targets`/`--only` runs the full plan exactly as before.

To preview a retry from a previous run report, call `preview_retry(root, jobs, output, report)` or pass `--retry-preview REPORT` (optionally with `--root` and `--output`); `report` is a root-relative report path and may equal `output`. Every result whose `status` is `failed` or `blocked` becomes a retry target, in current plan order regardless of report record order, and the returned object is `{"targets": [...], "jobs": [...]}`. The jobs cover the targets and all their prerequisites — including prerequisites the report marked `completed`, since rerunning manually reprocesses them, and shared prerequisites appear once — with the same fields, order and `target`/`prerequisite` reasons as `preview_plan` with targets. The report may cover a partial run: unrecorded tasks join the preview only when they are needed prerequisites, and unrelated branches are omitted. With no failed or blocked records the result is `{"targets": [], "jobs": []}`. The whole plan and the output path are validated first, even for an empty retry range, including unselected branches. The report must be a UTF-8 JSON object whose `results` is a list of objects; each `name` must exactly match a current task without repeats and `status` must be `completed`, `failed` or `blocked` (other fields are ignored and an empty list is valid). A missing, unreadable, non-UTF-8 or invalid-JSON report, wrong structure, unknown or duplicate names, illegal status, or a report path that is absolute or resolves (via symlinks) outside root all raise `ValueError`; the CLI prints `{"error": ...}` JSON and returns 2. `--retry-preview` cannot be combined with `--preview` or `--only`. A retry preview reads only the plan and the report: it never runs tasks, reads task inputs, creates directories or writes anything, success or failure leaves every existing file unchanged, and it does not promise the tasks would succeed (missing inputs, unknown operations and bad contents still preview). Ordinary runs remain driven solely by that run's results.

To run a manual retry from a previous run report, call `run_retry(root, jobs, output, report)` or pass `--retry REPORT` (honoring `--root` and `--output`); `report` is a root-relative report path and may equal `output`, in which case targets are taken from the content before it is overwritten. Every result whose `status` is `failed` or `blocked` becomes a retry target, in current plan order regardless of report record order, and the run covers the targets and all their direct and indirect prerequisites — including prerequisites the report marked `completed`, since a manual rerun reprocesses them; shared prerequisites run once. The report may cover a partial run: unrecorded tasks run only when they are necessary prerequisites, and unrelated branches neither read their inputs nor produce records. Execution order, failure records and blocking propagation are identical to `run_plan`, with dependency decisions based solely on this run's results; file read errors, unknown operations and invalid contents are recorded as `failed`, independent branches keep running, and blocked tasks keep the `blocked_by` semantics. The returned list and the output report describe the same scope: the report saves only this run's results and never copies old records. The CLI counts and exit codes follow an ordinary execution (`blocked` is added when any job in scope declares dependencies), and exit is 1 when any result is failed or blocked. With no retry targets `run_retry` returns `[]`, the CLI prints `{"completed": 0, "failed": 0}` and exits 0, and no task input is read, no directory created and the report left unchanged. The whole plan — names, dependencies, all input paths and output protection, including unselected branches and an empty retry range — is validated first. The report follows the same format and rules as `preview_retry`: missing, unreadable, non-UTF-8 or invalid JSON, unknown or duplicate names and illegal statuses raise `ValueError`, the CLI prints `{"error": ...}` JSON and returns 2 without running tasks, leaving existing files untouched. Failures creating the output directory or writing the report raise `OSError` (CLI exit 2 with the error JSON) and already-executed tasks are not undone. `--retry` cannot be combined with `--preview`, `--retry-preview` or `--only`. No timestamps or automatic retries are added; only the three existing file operations are supported.

The API is `execute_job(root, job)`, `run_plan(root, jobs, output, targets=None)`, `preview_plan(root, jobs, output, targets=None)`, `preview_retry(root, jobs, output, report)` and `run_retry(root, jobs, output, report)`. `preview_plan` takes the same arguments as `run_plan` and returns `{"jobs": [...]}` without running anything: it never reads job inputs, creates directories, writes the report or reads an old report, so missing input files, unknown operations and invalid file contents do not fail a preview (it does not promise the tasks would succeed). The jobs array covers the selected targets and every prerequisite — shared prerequisites appear once, independent branches are omitted — in the same order the run would process them. Each entry has only `name`, `depends_on` (declaration order, `[]` when omitted), `reason` and `required_by`: without targets every reason is `all` and `required_by` is `[]`; with targets explicit targets are `target` (even when they are also prerequisites of another target) and every other included job is `prerequisite`. `required_by` lists the explicit targets that need the job directly or indirectly, including a job that is itself a target, in original plan order without repeats, so swapping target arguments leaves the preview unchanged. The whole plan is still validated first — names, dependencies and every input path, including unselected branches — and the output path is checked against the root boundary, task inputs and (in the CLI) the plan file; any failure or illegal target raises `ValueError`, the CLI prints its `{"error": ...}` JSON, returns 2 and leaves existing reports untouched. The CLI flag `--preview` prints the same object and returns 0 instead of the execution summary; without it all run behavior, records, ordering, blocking, `--only` scoping, summary fields and exit codes are unchanged. `execute_job` keeps its original semantics and knows nothing about dependencies. All input, plan and report paths must be relative and resolve inside root, including symlinks; the pre-run input path checks apply to blocked jobs too. Reports cannot replace a job input; the CLI also protects its plan. Operations are implemented directly in Python: no shell commands, subprocess execution, schedules or retries are available. Only the current run's results drive dependency decisions — ordinary runs never read old reports (only `preview_retry` does, to build its preview, and `run_retry` does, solely to choose its targets). This is a local trusted-user utility rather than an OS sandbox; it does not isolate concurrent filesystem changes.

Run `python3 -B -m unittest -v` for deterministic outputs, failure records, path boundaries, symlinks and CLI validation.
