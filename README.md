# Job Planner

Run a small deterministic file-task plan and persist each result. Python 3.10+ and the standard library are sufficient.

`python3 job_planner.py samples/plan.json` runs three included jobs: line count, SHA-256 and CSV dimensions. It prints completed/failed counts and writes `.results/latest.json`. The plan refers to `samples/notes.txt` and `samples/sales.csv` inside the chosen root. Use `--root` to set that directory and `--output` for a relative report path. `samples/plan-dependencies.json` shows forward references, a failed branch with blocked downstream jobs, and an independent job still succeeding.

Supported operations are count-lines, sha256 and csv-summary. Jobs without dependencies run sequentially in plan order; results have no timestamps so identical inputs produce identical report content. Duplicate job names are rejected. Per-job file or operation errors are recorded and subsequent jobs continue. Exit codes are 0 when all jobs complete, 1 when any job fails or is blocked, and 2 for an invalid plan or report path.

A job may declare `"depends_on": [other job names]`; a missing key or empty list means no dependencies. Names match exactly and may point forward in the plan. The whole dependency graph is validated before anything runs: `depends_on` must be a list of nonblank names with no duplicates, and every name must exist, not be the job itself and not form a cycle. Any violation makes `run_plan` raise `ValueError`; the CLI prints its `{"error": ...}` JSON, returns 2 and leaves any existing report untouched.

On each pass the plan runs the earliest-in-plan pending job whose direct dependencies already have records; dependency-free jobs take part in the same choice. A job executes its operation only when every direct dependency `completed`. If any direct dependency is `failed` or `blocked`, the job does not read its input and is recorded with only `name`, `status: "blocked"` and `blocked_by` (every failing or blocked direct dependency, in `depends_on` order); blocked state propagates downstream and each task produces exactly one record. Results in the report are ordered by actual processing order. When at least one job has a nonempty `depends_on`, the CLI summary adds a `blocked` count (the `failed` count still covers operation failures only); plans without dependencies keep the original summary fields.

To run only part of a plan, pass `run_plan(root, jobs, output, targets=[...])` or repeat the CLI's `--only NAME` once per job. Each target is one exact job name (no case folding or trimming); the run covers the targets plus all their direct and indirect prerequisites — shared prerequisites run once and target order never changes execution order. The whole plan is still validated (names, dependencies, input path boundaries) before the scope is chosen, so errors in unselected branches reject the run. Jobs outside the scope are not read, produce no records and cannot affect the exit code; the report and the returned list contain only the jobs processed this run, and the CLI counts and the optional `blocked` field describe that same scope. An empty or non-list `targets`, non-string or blank entries, duplicates and unknown names all raise `ValueError` (CLI: `{"error": ...}` JSON, exit 2, no tasks run, existing report untouched). Omitting `targets`/`--only` runs the full plan exactly as before.

To preview a retry from a previous run report, call `preview_retry(root, jobs, output, report)` or pass `--retry-preview REPORT` (optionally with `--root` and `--output`); `report` is a root-relative report path and may equal `output`. Every result whose `status` is `failed` or `blocked` becomes a retry target, in current plan order regardless of report record order, and the returned object is `{"targets": [...], "jobs": [...]}`. The jobs cover the targets and all their prerequisites — including prerequisites the report marked `completed`, since rerunning manually reprocesses them, and shared prerequisites appear once — with the same fields, order and `target`/`prerequisite` reasons as `preview_plan` with targets. The report may cover a partial run: unrecorded tasks join the preview only when they are needed prerequisites, and unrelated branches are omitted. With no failed or blocked records the result is `{"targets": [], "jobs": []}`. The whole plan and the output path are validated first, even for an empty retry range, including unselected branches. The report must be a UTF-8 JSON object whose `results` is a list of objects; each `name` must exactly match a current task without repeats and `status` must be `completed`, `failed` or `blocked` (other fields are ignored and an empty list is valid). The whole file is parsed as strict JSON, so a bare `NaN`, `Infinity` or `-Infinity` constant is rejected anywhere it appears — nested in a `result`, in an extra top-level field or an entry's extra field, and even when `results` is empty or no record would be retried — while the same words written as JSON strings are harmless; legal JSON numbers keep their previous parsing here (out-of-float-range exponents included). A missing, unreadable, non-UTF-8 or invalid-JSON report, wrong structure, unknown or duplicate names, illegal status, or a report path that is absolute or resolves (via symlinks) outside root all raise `ValueError`; the CLI prints `{"error": ...}` JSON and returns 2. `--retry-preview` cannot be combined with `--preview` or `--only`. A retry preview reads only the plan and the report: it never runs tasks, reads task inputs, creates directories or writes anything, success or failure leaves every existing file unchanged, and it does not promise the tasks would succeed (missing inputs, unknown operations and bad contents still preview). Ordinary runs remain driven solely by that run's results.

To execute a manual retry from a previous run report, call `run_retry(root, jobs, output, report)` or pass `--retry REPORT` (optionally with `--root` and `--output`). Target selection and scope are exactly the retry preview's: the report's `failed`/`blocked` tasks become targets in current plan order, the run covers them plus every direct and indirect prerequisite (including ones the report marked `completed` — they are re-executed), shared prerequisites run once, unrecorded tasks join only as required prerequisites of a partial report, and unrelated branches are neither read nor recorded. Execution order, failure records and `blocked_by` propagation are `run_plan`'s; file-read failures, unknown operations and invalid contents are recorded `failed`, independent branches keep running, and dependency decisions use only this run's results. The returned list and the report at `output` contain only this run's records — old records are never copied — and the CLI counts describe that same scope with the same exit codes as an ordinary run (0 when nothing failed or blocked, otherwise 1). `report` may equal `output`: targets are taken from the content read before the overwrite. With no retry targets `run_retry` returns `[]` without reading task inputs, creating directories or rewriting the report, and the CLI prints `{"completed":0,"failed":0}` and exits 0. The whole plan — names, dependencies, every input path and output protection, including unselected branches and an empty retry scope — is validated first; report validation is identical to `preview_retry`'s (missing, unreadable, non-UTF-8, invalid JSON — including a bare `NaN`/`Infinity`/`-Infinity` constant anywhere in the file, even in an ignored field or an empty results list — wrong structure, unknown/duplicate names or illegal status all raise `ValueError`; the same words inside strings are legal), so such a report never starts a run, and the CLI prints error-only JSON and exits 2 without running or changing files. Creating the output directory or writing the report can raise `OSError` (CLI: error JSON, exit 2) after tasks have run; executed tasks are not undone. `--retry` cannot be combined with `--only`, `--preview` or `--retry-preview`.

To compare two existing reports read-only and see whether tasks recovered or changed, call `compare_reports(root, jobs, output, before, after)` or pass `--compare BEFORE AFTER` (with the usual plan argument, `--root` and `--output`). It returns `{"jobs": [...]}` in current plan order listing every task recorded in at least one report; each entry has only `name`, `before`, `after` and `change`. A side with no record is `null`; a present side keeps only `status` plus its matching payload — `result` (an object) for `completed`, `error` (a string) for `failed`, `blocked_by` for `blocked`, the latter emitted in current dependency declaration order. `change` is `added` when only the after report records the task, `removed` when only before does, `changed` when the statuses or payloads differ (including a different failure message), otherwise `unchanged`; an unrecorded task is never treated as failed. Comparison ignores report record order and extra fields: numbers nested anywhere in `result` compare by the exact decimal value the report expresses, so `1`, `1.0` and `1e0` are equal and negative zero equals zero, while `0.10000000000000001` differs from `0.1`, `9007199254740993.0` from `9007199254740992.0`, `2e400` from `1e400` and `1e-400` from `0` (whereas `1e400` equals `10e399`), all without float precision loss even beyond the float range; otherwise JSON value equality applies — booleans differ from numbers, numbers differ from strings with the same digits, object key order is irrelevant and array order is significant; `blocked_by` compares as a set. Both reports are fully validated before any comparison is returned: long decimals and syntactically legal exponents outside float range are accepted, while `NaN`, `Infinity` and `-Infinity` reject the report even inside ignored extra fields (the same words inside strings are harmless). The returned sides keep the report's numbers as numbers preserving their value rather than strings or rounded floats, and the CLI prints them as legal JSON numbers (never `Infinity`); trailing zeros and exponent spelling are not preserved. The whole plan (including unrecorded branches), every input path and the output path are validated first, exactly like a run, and the CLI also protects the plan file. The reports follow the retry report rules (UTF-8 JSON object with a `results` list of objects, names matching the plan with no repeats and valid statuses; missing, unreadable, non-UTF-8, invalid-JSON, absolute or symlink-escaping paths all raise `ValueError`), and this entry point additionally requires the status payload to be present and well shaped: `result` must be an object, `error` a string, and `blocked_by` a nonempty, duplicate-free array naming only the job's declared direct dependencies. `--compare` cannot be combined with `--only`, `--preview`, `--retry-preview` or `--retry`; the CLI prints error-only JSON and exits 2 on any validation failure or option conflict, while a valid comparison exits 0 even when records are failed or blocked. A comparison is strictly read-only: it never runs tasks, reads task inputs, creates directories or writes files, and `before` and `after` may name the same file.

To understand from a single report why tasks failed or stayed blocked, call `explain_report(root, jobs, output, report)` or pass `--explain REPORT` (with the usual plan argument, `--root` and `--output`). It returns `{"jobs": [...]}` in current plan order containing only the tasks the report records as `failed` or `blocked`; each entry has only `name`, `status` and `causes`. A `failed` task has exactly one cause — itself, `status: "failed"` with the report's `error` string preserved verbatim. A `blocked` task is explained by following that report's `blocked_by` references level by level: reaching a `failed` record stops that branch on it as a terminal cause, reaching a `blocked` record expands that record's own `blocked_by`, and reaching a task with no record stops on an `{"name", "status": "unrecorded", "error": null}` cause. Only the report is traced — current file contents and other declared dependencies are never used to infer a cause — and if any `blocked_by` chain reaches a task the report records as `completed`, the whole explanation raises `ValueError`. Causes are de-duplicated by task name and emitted in current plan order, independently of report record order; the report may be partial, and an unrecorded task appears only when it is a trace endpoint, never as its own job. With no failed or blocked records the result is `{"jobs": []}`. Validation mirrors `compare_reports` exactly: the whole plan (including unrecorded branches), every input path and the output path are checked first, and the report must satisfy the same path, encoding, structure, name, status and strict payload rules (`result` object, `error` string, nonempty duplicate-free `blocked_by` naming only declared direct dependencies); extra fields are ignored. That includes rejecting a bare `NaN`/`Infinity`/`-Infinity` constant anywhere in the report — nested in a `result`, in an extra field or at top level, even with empty `results` — while the same words inside strings stay legal and an error string containing them is returned verbatim. `--explain` cannot be combined with `--only`, `--preview`, `--retry-preview`, `--retry` or `--compare`; the CLI prints error-only JSON and exits 2 on any validation failure or option conflict, while a valid explanation exits 0 even when it contains failures. An explanation is strictly read-only: it reads only the plan and the named report, never task inputs, and it never runs tasks, creates directories or writes files; `report` may equal `output`.

To query one task's record across several reports read-only, call `query_history(root, jobs, output, reports, targets=None)` or repeat the CLI's `--history REPORT` (with the usual plan argument, `--root`, `--output` and optional `--only NAME`). `reports` is a nonempty list of root-relative report paths; each entry must be a nonblank string and repeats are allowed. Reports are shown strictly in the order given — nothing is sorted by name or modification time and no other reports are scanned — so a repeated path yields a repeated, equal history position. It returns `{"jobs": [...]}` in current plan order; each entry has only `name` and `history`, a list as long as `reports` whose slots are `{"report": ..., "record": ...}` with `report` the path verbatim. A slot is `null` when that report has no record for the task (a missing record is never a failure and is never filled in from a neighbouring report); a present record keeps only `status` plus its matching payload with the same rules as `compare_reports` — `result` (an object) for `completed`, `error` (a string) for `failed`, and `blocked_by` for `blocked`, emitted in current dependency declaration order, with extra fields ignored. Numbers nested anywhere in a `completed` record's `result` keep the exact decimal value the report expresses, exactly as in `compare_reports`: the API returns them as numbers preserving their value (never rounded to float, collapsed to zero or infinity, or turned into strings — `0.10000000000000001`, `9007199254740993.0`, `1e400` and `1e-400` survive), the CLI prints them as legal JSON numbers (trailing zeros and exponent spelling are not preserved), and `NaN`, `Infinity` or `-Infinity` constants anywhere in a report — even in ignored extra fields — reject the query, while the same words inside strings are harmless. Without `--only` only tasks appearing in at least one report are listed, so all-empty reports give `{"jobs": []}`. With targets the listed tasks are exactly those named: the prerequisite closure is not expanded, target argument order never changes plan order, and a task no report ever records still appears with an all-`null` history as long as the name exists in the plan; illegal targets raise `ValueError` exactly as elsewhere. The whole plan (including unrecorded branches), every input path and the output path are validated first, and then every report is validated with the compare report's path, UTF-8, structure, name, status and strict payload rules — including records outside the `--only` scope and every later report in the list — so an absolute or symlink-escaping path, a missing/non-UTF-8/invalid-JSON report, a malformed payload, an empty or non-list `reports`, or a blank/non-string entry all raise `ValueError` with no partial history returned. `--history` cannot be combined with `--preview`, `--retry-preview`, `--retry`, `--compare` or `--explain`; the CLI prints error-only JSON and exits 2 on any validation failure or option conflict, while a valid query exits 0 even when records are failed or blocked. A history query is strictly read-only: it reads only the plan and the named reports, never task inputs, and it never runs tasks, creates directories or writes files; a report may equal `output`.

To preview a retry range from several historical reports ordered oldest to newest, call `preview_history_retry(root, jobs, output, reports)` or repeat the CLI's `--history-retry REPORT` (with the usual plan argument, `--root` and `--output`). `reports` is a nonempty list of root-relative report paths; each entry must be a nonblank string and repeats keep separate positions. Reports are interpreted strictly in the order given — nothing is sorted by name or modification time and no other reports are scanned — so a repeated path yields a separate, later position. Each task is judged by the last report (highest index) containing a record of it: a newer report that omits the task never clears an older status. A task becomes a retry target exactly when its latest record is `failed` or `blocked`, and targets appear in current plan order regardless of report record order; a task whose latest record is `completed`, or that no report ever records, is not a target. The returned object has exactly `targets`, `jobs` and `sources`. `jobs` cover the targets and every direct and indirect prerequisite — prerequisites that completed in history or were never recorded are included too, shared prerequisites appear once and unrelated branches are omitted — with the same fields, processing order and `target`/`prerequisite` reasons as `preview_plan` with those targets. `sources` corresponds to `targets` one to one and in the same order; each entry has only `name` (the target), `status` (its latest status), `report` (the source path verbatim) and `index` (that report's zero-based position in `reports`). With no targets the result is `{"targets": [], "jobs": [], "sources": []}`. The history only selects the range: the new run's dependency decisions still use only that run's own results, never inherited records. The whole plan (including unselected branches), every input path and the output path are validated first, exactly like a run, and then every report is fully validated with the path, UTF-8, structure, name, status and strict payload rules of `query_history` — including tasks that are not selected, older records a newer report overrides and every later report in the list — so an absolute or symlink-escaping path, a missing/non-UTF-8/invalid-JSON report, a malformed payload, an empty or non-list `reports`, or a blank/non-string entry all raise `ValueError` with no partial result returned. The whole file is strict JSON: a bare `NaN`, `Infinity` or `-Infinity` constant rejects any report even inside an ignored extra field, while the same words inside strings and syntactically legal JSON numbers (out-of-float-range exponents included) are accepted. `--history-retry` cannot be combined with `--only`, `--record-reasons` or any execution, preview or report-query option (`--preview`, `--retry-preview`, `--retry`, `--compare`, `--explain`, `--history`, `--execution`, `--changed`, `--run-changed`, `--run-history-retry`); the CLI prints error-only JSON and exits 2 on any validation failure or option conflict, while a valid preview prints the object and exits 0 even when records are failed or blocked. The preview is strictly read-only: it reads only the plan and the named reports (a report may equal `output`), never task inputs, and it never runs tasks, creates directories or writes files.

To execute the retry range a history retry preview describes, call `run_history_retry(root, jobs, output, reports, record_reasons=False)` or repeat the CLI's `--run-history-retry REPORT` (with the usual plan argument, `--root` and `--output`). `reports` follows the preview's rules exactly: a nonempty list of nonblank root-relative report paths, ordered oldest to newest, repeats keeping separate later positions and no other file scanned. Target selection is identical — each task is judged by the last report containing a record of it, a later missing record never clears an older status, and only tasks whose latest record is `failed` or `blocked` become targets in current plan order — and the scope and processing order are exactly what `preview_history_retry` shows: every prerequisite is re-executed (even ones that completed in history or were never recorded), shared prerequisites run once and unrelated branches are neither read nor recorded. Dependency decisions use only this run's results: file-read failures, unknown operations and invalid contents are recorded `failed` (the historical error text is never reused), independent branches keep running, blocked tasks never read their input and `blocked_by` lists every failed or blocked direct dependency in declaration order. The returned list holds this run's records in processing order and `output` contains exactly those records under `results` — old records are never mixed in. A report path (or several paths that are aliases of the same file) may equal `output`: the range is taken from the full history content read before the overwrite. The CLI statistics and exit codes are an ordinary run's (0 when nothing failed or blocked, otherwise 1). With no targets the function returns `[]` without reading task inputs, creating directories or changing any report (an existing `output` is left untouched), and the CLI prints `{"completed":0,"failed":0}` and exits 0. The whole plan — names, dependencies, every input path and output protection, including unselected branches and an empty scope — is validated before the scope is chosen, and then every report is fully validated with the history preview's path, UTF-8, structure, name, status and strict payload rules, including non-target tasks, overridden older records and reports after the newest record; an empty or non-list `reports`, a blank/non-string entry, an absolute or symlink-escaping path, or a missing/non-UTF-8/invalid-JSON report (a bare `NaN`/`Infinity`/`-Infinity` constant anywhere rejects it; the same words inside strings are fine) all raise `ValueError` before any task runs or file changes, and the CLI prints error-only JSON and exits 2. Creating the output directory or writing the report can raise `OSError` (CLI: error JSON, exit 2) after tasks have run; executed tasks are not undone. With `record_reasons=True` and at least one target the report gains the usual `execution` object: `mode` is `"retry"`, `targets` and `jobs` match the history preview exactly (its `sources` are not saved), `jobs` match `results` in name and order, and the existing `query_execution`/`--execution` reader reads it back like any other retry execution; with no targets nothing is written. A non-boolean `record_reasons` raises `ValueError`. `--run-history-retry` cannot be combined with `--only` or any preview or report-query option (`--preview`, `--retry-preview`, `--retry`, `--compare`, `--explain`, `--history`, `--history-retry`, `--execution`, `--changed`, `--run-changed`); only the plan argument, `--root`, `--output` and `--record-reasons` are allowed.

To preview which tasks a set of changed input files would affect, call `preview_changes(root, jobs, output, changed_inputs)` or repeat the CLI's `--changed PATH` (with the usual plan argument, `--root` and `--output`). `changed_inputs` is a list of root-relative path strings; an empty list is allowed, every entry must be a nonblank string, and each path is resolved exactly like a plan input path — absolute paths and paths resolving (via symlinks) outside root raise `ValueError`, even when they would match nothing. Paths resolving to the same file are merged and argument order never changes the result. Matching uses resolved paths only: files need not exist and are never read, and a legal path matching no task input simply produces no targets. The result is `{"targets": [...], "jobs": [...]}`: targets are the tasks whose resolved input path was directly changed plus every task downstream of them along declared dependencies, each once, in original plan order; jobs cover the targets and all their prerequisites, each once, in the usual preview processing order with the same `depends_on`, `reason` (`target`/`prerequisite`) and `required_by` semantics as `preview_plan` with targets, plus a `triggered_by` field listing the directly changed tasks that can reach the job along dependency edges, in original plan order — a directly changed task lists itself, and jobs included only as prerequisites get `[]`. With no changed inputs or no matching task the result is `{"targets": [], "jobs": []}`. The whole plan, every input path and the output path are validated exactly like a run before the scope is chosen, even for an empty result; any violation or an illegal `changed_inputs` raises `ValueError`, and the CLI prints `{"error": ...}` JSON and exits 2 while a valid preview prints the object and exits 0. `--changed` cannot be combined with `--only`, `--preview`, `--retry-preview`, `--retry`, `--compare`, `--explain` or `--history`. A change preview is strictly read-only: it reads only the plan, never task inputs, old reports or file contents, and it never runs tasks, creates directories or writes files.

To execute the tasks affected by a set of changed input files, call `run_changes(root, jobs, output, changed_inputs)` or repeat the CLI's `--run-changed PATH` (with the usual plan argument, `--root` and `--output`). The scope is exactly what `preview_changes` would show for the same paths: the tasks whose resolved input path was directly changed plus every downstream dependent become targets in plan order, the run covers them plus every direct and indirect prerequisite, and shared prerequisites run once. `changed_inputs` follows the preview's rules — a list of root-relative nonblank path strings (an empty list is allowed), each resolved like a plan input path so absolute or symlink-escaping paths raise `ValueError`, matched by resolved path only: files need not exist and are never read, duplicates, aliases and argument order change nothing, and a legal path matching no task input produces no targets. Execution order, failure records and `blocked_by` propagation are `run_plan`'s: input read failures, unknown operations and invalid contents are recorded `failed` with their error, independent branches keep running, blocked tasks never read their input, `blocked_by` lists every failed or blocked direct dependency in declaration order, and dependency decisions use only this run's results. The returned list holds this run's records in actual processing order and the report at `output` contains exactly those records under `results`, replacing any prior content; tasks outside the scope are not read, produce no records and cannot affect the exit code, and the CLI counts describe that same scope with the usual summary fields and exit codes (0 when nothing failed or blocked, otherwise 1). With no changed inputs or no matching task `run_changes` returns `[]` without reading task inputs, creating directories or rewriting the report, and the CLI prints `{"completed":0,"failed":0}` and exits 0. The whole plan — names, dependencies, every input path and output protection, including unselected branches and an empty scope — is validated before the scope is chosen; any violation or an illegal `changed_inputs` raises `ValueError`, and the CLI prints error-only JSON and exits 2 without running tasks or changing files. Creating the output directory or writing the report can raise `OSError` (CLI: error JSON, exit 2) after tasks have run; executed tasks are not undone. `--run-changed` cannot be combined with `--only`, `--preview`, `--retry-preview`, `--retry`, `--compare`, `--explain`, `--history` or `--changed`.

To record why a run happened alongside its results, pass `record_reasons=True` to `run_plan`, `run_retry`, `run_history_retry` or `run_changes`, or add the CLI flag `--record-reasons`. The option defaults to off: with it absent or false every report, returned list, CLI summary line and exit code is exactly as before. When it is on and the run processes at least one task, the report written to `output` gains one extra top-level field — `execution` — while `results`, the returned list, the CLI statistics and the exit code are unchanged; only `output` is ever written (no extra files or directories, no timestamps). `execution` is an object with exactly `mode`, `targets` and `jobs`. `mode` is `"all"` for an unfiltered plan run, `"only"` for an explicit `targets`/`--only` selection (even when that selection names every job), `"retry"` for a report-derived retry and `"changes"` for a changed-input run. `targets` lists this run's targets in current plan order: every plan job for `all`, the explicitly named jobs for `only`, the old report's `failed`/`blocked` jobs for `retry`, and the directly changed tasks plus every downstream dependent for `changes`. `jobs` uses the fields and semantics of the matching public preview — the `preview_plan` entries for ordinary runs (`all` reasons and empty `required_by` for a full run, otherwise `target`/`prerequisite`), `preview_retry` for single-report retries, `preview_history_retry` for multi-report history retries (without that preview's `sources`) and `preview_changes` (including `triggered_by`) for change runs — with the same job names, in the same order, as the run's `results`. Shared prerequisites therefore appear exactly once; failed and blocked jobs keep the selection reasons their preview assigned them and the reasons are never rewritten from this run's outcomes. With no retry targets or no changed-input match the run still returns `[]`, writes no report and creates no directory even with the option on. For a retry whose `report` equals `output`, and for a history retry where any report (or an alias of one) equals `output`, the reasons come from the content read before the overwrite; target ordering, history report order and repeats, changed-path ordering and aliases of the same file follow the existing preview rules and cannot change the recorded reasons. `record_reasons` must be a plain boolean — any other value (including `0` or `1`) raises `ValueError`; the CLI's `--record-reasons` cannot be combined with `--preview`, `--retry-preview`, `--changed`, `--compare`, `--explain` or `--history` (the CLI prints error-only JSON and exits 2). Reports carrying `execution` need no migration: every report reader (`preview_retry`, `run_retry`, `run_history_retry`, `compare_reports`, `explain_report`, `query_history`, `preview_history_retry`) treats it as an ignored extra field under the usual extra-field rules, and a later run without the flag writes a report without it again.

To read back why a recorded run happened, call `query_execution(root, jobs, output, report)` or pass `--execution REPORT` (with the usual plan argument, `--root` and `--output`). It returns an object with only an `execution` field: the report's recorded `execution` — `mode`, `targets` and `jobs` — reduced to the published reason fields (each job keeps only `name`, `depends_on`, `reason` and `required_by`, plus `triggered_by` for `changes` mode), with every array in the order the report recorded and every value preserved as recorded — the historical selection is never recomputed, and failed or blocked records do not rewrite reasons. A report without an `execution` field (written before reasons could be recorded, or with the option off) and a report with empty `results` both return `{"execution": null}`. Validation mirrors `compare_reports` first: the whole plan, every input path and the output path are checked, and the report's `results` must satisfy the compare report's strict path, encoding, structure, name, status and payload rules, so a partial report is legal. The whole file is strict JSON, so a bare `NaN`/`Infinity`/`-Infinity` constant rejects the query anywhere it appears — nested in a `result`, in a record's or top-level extra field, or inside `execution` (including its own extra fields) — even when `results` is empty, no `execution` is present or the query would otherwise return `null`; the same words inside strings are harmless. A present `execution` must then be an object whose `mode` is one of `all`/`only`/`retry`/`changes`, whose `targets` is a nonempty duplicate-free list of current plan job names, and whose `jobs` is a nonempty list of objects matching `results` in name and order and covering every target; each job's `depends_on` must equal the current declaration, `required_by` (and `triggered_by`, required in `changes` mode) may reference only targets, and no task-name list may repeat. For `all` the targets must cover the whole plan and every job needs reason `all` with an empty `required_by`; otherwise each job's reason must be `target` or `prerequisite` according to whether it is a target. Beyond types, references and these correspondences the recorded reason lists are trusted as-is. Missing fields, wrong types, unknown references, an illegal mode, a broken correspondence or an `execution` that is `null` all raise `ValueError`; extra fields are ignored. `--execution` cannot be combined with `--only`, `--record-reasons` or any other execution, preview or report-query option; the CLI prints error-only JSON and exits 2 on any validation failure or conflict, while a valid query exits 0. The query is strictly read-only — it reads only the plan and the named report (`report` may equal `output`), never task inputs, and it never runs tasks, creates directories or writes files.

The API is `execute_job(root, job)`, `run_plan(root, jobs, output, targets=None, record_reasons=False)`, `run_retry(root, jobs, output, report, record_reasons=False)`, `run_history_retry(root, jobs, output, reports, record_reasons=False)`, `run_changes(root, jobs, output, changed_inputs, record_reasons=False)`, `preview_plan(root, jobs, output, targets=None)`, `preview_retry(root, jobs, output, report)`, `preview_history_retry(root, jobs, output, reports)`, `preview_changes(root, jobs, output, changed_inputs)`, `compare_reports(root, jobs, output, before, after)`, `explain_report(root, jobs, output, report)`, `query_history(root, jobs, output, reports, targets=None)` and `query_execution(root, jobs, output, report)`. `preview_plan` takes the same arguments as `run_plan` and returns `{"jobs": [...]}` without running anything: it never reads job inputs, creates directories, writes the report or reads an old report, so missing input files, unknown operations and invalid file contents do not fail a preview (it does not promise the tasks would succeed). The jobs array covers the selected targets and every prerequisite — shared prerequisites appear once, independent branches are omitted — in the same order the run would process them. Each entry has only `name`, `depends_on` (declaration order, `[]` when omitted), `reason` and `required_by`: without targets every reason is `all` and `required_by` is `[]`; with targets explicit targets are `target` (even when they are also prerequisites of another target) and every other included job is `prerequisite`. `required_by` lists the explicit targets that need the job directly or indirectly, including a job that is itself a target, in original plan order without repeats, so swapping target arguments leaves the preview unchanged. The whole plan is still validated first — names, dependencies and every input path, including unselected branches — and the output path is checked against the root boundary, task inputs and (in the CLI) the plan file; any failure or illegal target raises `ValueError`, the CLI prints its `{"error": ...}` JSON, returns 2 and leaves existing reports untouched. The CLI flags `--preview` and `--retry-preview` print those objects and return 0 instead of executing; `--retry` performs the execution described above. Without any retry or preview option all run behavior, records, ordering, blocking, `--only` scoping, summary fields and exit codes are unchanged. `execute_job` keeps its original semantics and knows nothing about dependencies. All input, plan and report paths must be relative and resolve inside root, including symlinks; the pre-run input path checks apply to blocked jobs too. Reports cannot replace a job input; the CLI also protects its plan. Operations are implemented directly in Python: no shell commands, subprocess execution, schedules, timestamps or automatic retries are available — a retry happens only when requested manually. Only the current run's results drive dependency decisions; `run_retry` reads the historical report solely to choose its targets, never to inherit records. This is a local trusted-user utility rather than an OS sandbox; it does not isolate concurrent filesystem changes.

Run `python3 -B -m unittest -v` for deterministic outputs, failure records, path boundaries, symlinks and CLI validation.
