# Job Planner

Run a small deterministic file-task plan and persist each result. Python 3.10+ and the standard library are sufficient.

`python3 job_planner.py samples/plan.json` runs three included jobs: line count, SHA-256 and CSV dimensions. It prints completed/failed counts and writes `.results/latest.json`. The plan refers to `samples/notes.txt` and `samples/sales.csv` inside the chosen root. Use `--root` to set that directory and `--output` for a relative report path. `samples/plan-dependencies.json` shows forward references, a failed branch with blocked downstream jobs, and an independent job still succeeding.

Supported operations are count-lines, sha256 and csv-summary. Jobs without dependencies run sequentially in plan order; results have no timestamps so identical inputs produce identical report content. Duplicate job names are rejected. Per-job file or operation errors are recorded and subsequent jobs continue. Exit codes are 0 when all jobs complete, 1 when any job fails or is blocked, and 2 for an invalid plan or report path.

A job may declare `"depends_on": [other job names]`; a missing key or empty list means no dependencies. Names match exactly and may point forward in the plan. The whole dependency graph is validated before anything runs: `depends_on` must be a list of nonblank names with no duplicates, and every name must exist, not be the job itself and not form a cycle. Any violation makes `run_plan` raise `ValueError`; the CLI prints its `{"error": ...}` JSON, returns 2 and leaves any existing report untouched.

On each pass the plan runs the earliest-in-plan pending job whose direct dependencies already have records; dependency-free jobs take part in the same choice. A job executes its operation only when every direct dependency `completed`. If any direct dependency is `failed` or `blocked`, the job does not read its input and is recorded with only `name`, `status: "blocked"` and `blocked_by` (every failing or blocked direct dependency, in `depends_on` order); blocked state propagates downstream and each task produces exactly one record. Results in the report are ordered by actual processing order. When at least one job processed in the run has a nonempty `depends_on`, the CLI summary adds a `blocked` count (the `failed` count still covers operation failures only); plans without dependencies keep the original summary fields.

Pass `--only TASK` (repeatable) to run just one or more named targets together with every direct and indirect prerequisite; the original three-argument `run_plan` call, or `targets=None`, still runs the whole plan, and a CLI invocation without `--only` keeps the original behavior. Targets are matched exactly with no case folding or trimming. `targets` must be a nonempty list of strings: an empty list, a non-list, a non-string or blank element, a repeated name or an unknown name all raise `ValueError`; the CLI prints only its `{"error": ...}` JSON, returns 2, runs nothing and leaves any existing report unchanged. Shared prerequisites of several targets run once, and the order in which targets are declared never changes execution order.

The selected scope never grows into a target's downstream or into unrelated jobs: out-of-scope jobs are not read, produce no records and do not affect the run's success, so an unselected job whose input is missing or whose operation is unsupported causes no failure (it is still covered by the pre-run validation below). The report is still written to the given output path, and both the report and the API return only this run's records in processing order, with no timestamps and without carrying over any old report. The CLI summary counts the current run only; `blocked` appears only when the scope contains a job with a nonempty `depends_on`. Exit codes are unchanged: 0 when everything processed completes, 1 when a processed job fails or is blocked. When a shared prerequisite fails, targets depending on it are blocked under the usual propagation rule while an independent selected target can still complete.

The API is `execute_job(root, job)` and `run_plan(root, jobs, output, targets=None)`. `execute_job` keeps its original semantics and knows nothing about dependencies. Before the scope is chosen the whole plan is validated — names, dependencies (including every unselected branch) and input path boundaries — so an existing error in an unselected branch still rejects the run, executes nothing and does not rewrite the report. All input, plan and report paths must be relative and resolve inside root, including symlinks; the pre-run input path checks apply to blocked jobs too. Reports cannot replace a job input (any job in the plan, even one outside the scope); the CLI also protects its plan. Operations are implemented directly in Python: no shell commands, subprocess execution, schedules or retries are available. Only the current run's results drive dependency decisions — old reports are never read. This is a local trusted-user utility rather than an OS sandbox; it does not isolate concurrent filesystem changes.

Run `python3 -B -m unittest -v` for deterministic outputs, failure records, path boundaries, symlinks and CLI validation.
