# Job Planner

Run a small deterministic file-task plan and persist each result. Python 3.10+ and the standard library are sufficient.

`python3 job_planner.py samples/plan.json` runs three included jobs: line count, SHA-256 and CSV dimensions. It prints completed/failed counts and writes `.results/latest.json`. The plan refers to `samples/notes.txt` and `samples/sales.csv` inside the chosen root. Use `--root` to set that directory and `--output` for a relative report path. `samples/plan-dependencies.json` shows forward references, a failed branch with blocked downstream jobs, and an independent job still succeeding.

Supported operations are count-lines, sha256 and csv-summary. Jobs without dependencies run sequentially in plan order; results have no timestamps so identical inputs produce identical report content. Duplicate job names are rejected. Per-job file or operation errors are recorded and subsequent jobs continue. Exit codes are 0 when all jobs complete, 1 when any job fails or is blocked, and 2 for an invalid plan or report path.

A job may declare `"depends_on": [other job names]`; a missing key or empty list means no dependencies. Names match exactly and may point forward in the plan. The whole dependency graph is validated before anything runs: `depends_on` must be a list of nonblank names with no duplicates, and every name must exist, not be the job itself and not form a cycle. Any violation makes `run_plan` raise `ValueError`; the CLI prints its `{"error": ...}` JSON, returns 2 and leaves any existing report untouched.

On each pass the plan runs the earliest-in-plan pending job whose direct dependencies already have records; dependency-free jobs take part in the same choice. A job executes its operation only when every direct dependency `completed`. If any direct dependency is `failed` or `blocked`, the job does not read its input and is recorded with only `name`, `status: "blocked"` and `blocked_by` (every failing or blocked direct dependency, in `depends_on` order); blocked state propagates downstream and each task produces exactly one record. Results in the report are ordered by actual processing order. When at least one job has a nonempty `depends_on`, the CLI summary adds a `blocked` count (the `failed` count still covers operation failures only); plans without dependencies keep the original summary fields.

To run only part of a plan, pass `run_plan(root, jobs, output, targets=[...])` or repeat the CLI's `--only NAME` once per job. Each target is one exact job name (no case folding or trimming); the run covers the targets plus all their direct and indirect prerequisites — shared prerequisites run once and target order never changes execution order. The whole plan is still validated (names, dependencies, input path boundaries) before the scope is chosen, so errors in unselected branches reject the run. Jobs outside the scope are not read, produce no records and cannot affect the exit code; the report and the returned list contain only the jobs processed this run, and the CLI counts and the optional `blocked` field describe that same scope. An empty or non-list `targets`, non-string or blank entries, duplicates and unknown names all raise `ValueError` (CLI: `{"error": ...}` JSON, exit 2, no tasks run, existing report untouched). Omitting `targets`/`--only` runs the full plan exactly as before.

Before triggering a run, call `preview_plan(root, jobs, output, targets=None)` (same parameters as `run_plan`) or pass `--preview` to the CLI. It returns `{"jobs": [...]}`, covering the selected targets and every prerequisite in the same scope and processing order an actual run would use; shared prerequisites appear once and swapping target arguments leaves the preview unchanged. Each entry has exactly `name`, `depends_on` (direct dependencies in declaration order, `[]` when omitted), `reason` and `required_by`, with no execution status or result. Without targets every job's reason is `all` and `required_by` is `[]`; with targets, explicit targets are `target` (even when also another target's prerequisite) and every other included job is `prerequisite`. `required_by` lists the explicit targets that need the job directly or indirectly, including the job itself when it is a target, in the targets' plan order with no duplicates. The CLI prints the same JSON object and returns 0 without an execution summary. A preview executes nothing: it never reads task input contents, never creates directories or writes a report and never reads an old report, so missing inputs, unknown operations and invalid file contents do not fail it — the preview does not promise the jobs will succeed. The whole plan is still validated first (names, dependencies, every input path, the report root/symlink boundary and input-overwrite rule, plus the CLI's plan-file protection), including unselected branches; any validation failure or illegal target makes `preview_plan` raise `ValueError` and the CLI print its `{"error": ...}` JSON, return 2 and leave existing reports untouched.

The API is `execute_job(root, job)`, `run_plan(root, jobs, output, targets=None)` and `preview_plan(root, jobs, output, targets=None)`. `execute_job` keeps its original semantics and knows nothing about dependencies. All input, plan and report paths must be relative and resolve inside root, including symlinks; the pre-run input path checks apply to blocked jobs too. Reports cannot replace a job input; the CLI also protects its plan. Operations are implemented directly in Python: no shell commands, subprocess execution, schedules or retries are available. Only the current run's results drive dependency decisions — old reports are never read. This is a local trusted-user utility rather than an OS sandbox; it does not isolate concurrent filesystem changes.

Run `python3 -B -m unittest -v` for deterministic outputs, failure records, path boundaries, symlinks and CLI validation.
